# Structured Proof

用固定关键词块把证明写成单向链，每块只讲一件事，块之间只用 BY/THEREFORE/SUFFICES 连接。关键词只用下表三层里的，不自创；块头一律 `**KEYWORD:**` 加粗。

## logic words（推导骨架）

| 类别 | 关键词 |
| ---- | ------ |
| 对象 | `LET`(令), `DEFINE`(定义) |
| 上下文 | `GIVEN`(外部事实), `ASSUME`(证明假设) |
| 契约 | `REQUIRE`(前置条件), `ENSURE`(后置条件), `INVARIANT`(不变量) |
| 量词 | `FORALL`(∀), `EXISTS`(∃), `EXISTS!`(∃!) |
| 逻辑 | `WHERE`(限定范围), `IF ... THEN`(充分条件), `IFF`(重要条件), `NOT`, `AND`, `OR` |
| 目标 | `GOAL`(证明目标), `CLAIM`(将证明的中间命题) |
| 推导状态 | `HAVE`(已经成立的条件), `CONSIDER`(考虑表达式中的一部分), `SUFFICES`(只需要) |
| 分支 | `CASE`, `OTHERWISE`(其他情况) |
| 推理 | `BY`(正式证明依据), `BECAUSE`(自然语言解释), `THEREFORE`(所以) |
| 特殊证明 | `CONTRADICTION`(反证), `WLOG`(不失一般性) |
| 结束 | `QED` |

## semantic layer（解释层，不进主链）

| 作用 | 关键词 | 含义 |
| ---- | ------ | ---- |
| 解释 | `INTERPRET` | 公式、对象、推导或结论“意味着什么” |
| 直觉 | `INTUITION` | 非严格的直观理解 |
| 动机 | `MOTIVATION` | 为什么要这样定义、假设、构造或推导 |
| 注意 | `NOTE` | 值得注意的补充事实、提醒或备注 |
| 影响 | `IMPLICATION` | 这个结果会导致什么、为什么重要 |
| 检查 | `CHECK` | 从量纲、极限、特殊情况验证合理性 |
| 限制 | `CAVEAT` | 适用条件、近似条件、限制和例外 |

## statement layer（陈述层，概念文件用）

| 作用 | 关键词 | 含义 |
| ---- | ------ | ---- |
| 概念 | `CONCEPT` | 介绍一个概念及其基本思想 |
| 定义 | `DEFINITION` | 严格的数学定义 |
| 性质 | `PROPERTY` | 对象具有的性质 |
| 命题 | `PROPOSITION` | 可证明的数学陈述 |
| 引理 | `LEMMA` | 为主要结果准备的辅助命题 |
| 定理 | `THEOREM` | 重要的、需证明的结论 |
| 推论 | `COROLLARY` | 从已有定理直接推导出的结论 |
| 示例 | `EXAMPLE` | 具体实例 |

## 链式规则

1. 主链单向：GIVEN → HAVE → SUFFICES → 归约 → THEREFORE。缺条件回 GIVEN 补，不回头改。
2. 每个 HAVE 只推一步；多步拆块，中间用 CONSIDER 拎项。
3. BY 只引用已编号的式子或已存在的文件，不引用叙述文字。
4. 归约到已解决的引理即停，不重证；无噪声极限等自检放 CHECK，不进主链。
5. 解释性文字只用 semantic layer 块写，与主链分开。
6. 主链上所有后面要用的方程都要打 `\tag{n}` 编号（GIVEN 的条件、HAVE 的每步结果），THEREFORE 前用 BY 列出联立的编号；编号全文件连续，Phase 之间接着编，不重起。

## 文件类型边界（CON / PRF / RES）

| 文件 | 定位 | 内容边界 | 引用方向 |
| ---- | ---- | -------- | -------- |
| `CON-*`（Concept，基础概念/通用词典） | 最底层基石 | 原子定义、公理、经典引理（如 `CON-SWAP`、`CON-Schur_Lemma`）；不绑定具体实验协议参数（如 $M, K$、特定噪声模型），不挂长篇自证 | 被 `PRF-*`、`RES-*` 自下而上引用 |
| `PRF-*`（Proof，具体推导与证明链） | 单命题推导 | 针对单一命题或分步归约的完整算式推导（`GIVEN -> HAVE -> SUFFICES -> BY -> THEREFORE -> QED`） | 引用 `CON-*` 或底层 `PRF-*`，向上支撑 `RES-*` |
| `RES-*`（Result，研究结果/协议方案/综合定理） | 完整研究产出 | 协议方案或综合定理（理想无噪或含噪鲁棒均可，如 `RES-Classical_Shadow`、`RES-Hamming_Distance`、`RES-Robust_Hamming`）：协议设定（`ASSUME`/`REQUIRE`）、核心构造（如估计器公式）、结论性质（`PROPERTY`）、解析自检（`CHECK`）与按需可选的数值验证（文件末尾二级标题 `## VERIFY`，含状态、`note/VER-<名称>/` 目录与按验证项分点的内容） | 用 `BY: [PRF-*]` 链接下层证明，被 `TOP-*` 索引 |

判据：绑定具体协议/实验参数即 `RES-*`；纯推导链即 `PRF-*`；无协议参数的原子陈述即 `CON-*`。

## 符号与文件纪律

- 一字母一物，发现重名立刻改名；下标体系一旦选定（比特/对/实验）全文一致。
- md 行内 `$...$`，独立公式 `$$` 块；`\tag{n}` 不放 `split` 环境内。
- 跨文件引用走 BY 链，不抄正文；只改当前任务必需处。
- 数值验证（**按需可选，非必选**）：很多 `RES-*` 的结论是已知明确结果，无需每次都跑数值验证。仅在需要时于 `RES-*` 文件末尾以**二级标题 `## VERIFY`**（而非块级 `**VERIFY:**` 关键词）呈现数值验证，含三项简短信息——**状态**（如已通过 / 待验证 / 仅验证某特例）、**目录**（`note/VER-<名称>/`，存放数值验证脚本与数据，已在 git 中忽略）、**内容**（按所验证的物理量/结论分点列出「分别验证了什么」，不堆砌具体数值参数与误差数字，不写成一大段）。**行为准则**：完成 `RES-*` 或相关证明整理后，不要自动强行创建 `VER-*/` 跑数值验证，而是仅简短提醒/询问用户是否需要对该结果做数值验证，待用户确认后再执行。
- 推导理解标记（标题级，只标未深入推导项）：自己推导或 AI 辅助但经交互已基本完全理解的章节不加任何标记；仅当某节主要由 AI 独立生成、尚未亲自逐行推导消化时，在该节标题末尾加 `[AI]`（如 `# <标题> [AI]`、`## Phase 2: ... [AI]`），待消化后再移除。
